# Devbox Anywhere v1.4.0 — Multi-channel shared sessions with multi-agent projects

> **For Hermes:** implement task-by-task with TDD and per-task independent review, exactly as v1.2.0/v1.3.0 shipped. Never weaken the installer, source-trust, secret, private-network, one-writer-per-checkout, or "not a sandbox" boundaries. Real behavior must be smoke-tested on a devbox before tag/release.

**Goal:** One project = one durable tmux session on the devbox (the shared "room"), reachable interchangeably from any channel Hermes is connected to (terminal, Telegram, Slack, …). Multiple agents can work the same project in parallel, each in its own tmux window backed by its own git worktree + branch, so they never collide. Switch channels or agents freely; the box is the single source of truth.

**Key architectural facts:**
- **Hermes manages channels.** Telegram/Slack/etc. are connected, authenticated, and allow-listed in Hermes configuration — NOT in this repo. devbox-anywhere provides only the box-side session layer and the guide for pointing Hermes channels at it. No adapters, no per-channel auth code here.
- **The tmux session is the shared session.** Every channel is a thin control surface (`send`/`capture`) onto the same tmux target via the existing `tmuxctl` (`scripts/hermes`).
- **The unit of isolation is the checkout, not the session.** The project's real collision risk is two agents writing one working tree. Model: `project → one session → {agent: (window, worktree, branch)}`. The turn/one-writer lock is **per worktree**.

**Tech stack:** existing `scripts/hermes` (`tmuxctl`: `ls/peek/send/run/wait`, NUL-safe SSH transport), tmux windows, `git worktree`, the `scripts/devbox-anywhere` harness, `tests/run.sh`. Base: `main` after v1.3.0 (`028b3cb`).

---

## The model

```
project   → one tmux session            shared "room"; any Hermes channel resolves to it
agent     → one window + one worktree    its own checkout + branch = true parallel isolation
channel   → project:window (one agent) | session (see all)   channels live in Hermes config
turn-lock → per worktree                 enforces one-writer-per-checkout (advisory, not security)
```

Scales down cleanly: one agent = one window + one worktree = identical to today, zero overhead. Multi-agent machinery only appears when a second agent is added.

## Core decisions (settled with Philippe)

- **D1. Channels stay in Hermes config.** This repo does not build channel adapters or per-channel allow-lists. It documents how to wire an existing Hermes channel to a `project:window` tmux target.
- **D2. Model 2 is the default.** project → session; agent → window + git worktree + branch. Model 3 (fully separate session per agent) is available for genuinely separate sub-projects but is not the default.
- **D3. Turn-lock is per worktree.** One writer per checkout, enforced by an advisory lock keyed on the worktree path. Never presented as a security or sandbox boundary; tmux/git provide no native locking.
- **D4. Agent lives in the pane; channels drive it.** Channels do not spawn their own agent. Dead agent recovers via the CLI's own resume (`claude --resume` / `codex resume`) against persistent `~/.claude`/`~/.codex` bind mounts.
- **D5. Chat render policy.** Line-oriented command/response → `capture-pane` snapshots + new-line streaming to chat. Full-screen TUIs do NOT mirror to chat — documented limitation.
- **D6. Telegram UX shift (accept explicitly).** A project topic drives its session/agent via `tmuxctl`, rather than being a separate Hermes chat. User-visible change; called out in release notes.
- **D7. Scope split.** v1.4.0 = core box-side primitives + wiring guide. Conveniences (cross-worktree merge/reconcile, richer multi-agent chat status, cross-agent handoff notes) deferred to v1.4.1.

**Resolved answers (following the recommendation):**
- **OQ1 — Turn-lock model: EXPLICIT `take`/`release`.** Agent+human sharing one worktree is exactly where a silent auto-timeout corrupts a mid-edit. Explicit is predictable; an auto-expire exists only as a stale-lock safety net (reclaimable after N minutes idle), never as the primary hand-off mechanism.
- **OQ2 — Worktree location: `/data/devbox/project/.worktrees/<agent>`.** Under the existing persistent, root-controlled data root, so worktrees survive rebuilds like all other state. The `.worktrees/` dir is created with the same ownership/mode discipline as the other `/data/devbox` subdirs.
- **OQ3 — Agent/window naming: REQUIRED `<project>-<agent>` convention.** Channels must address agents unambiguously; the helper rejects free-form or colliding names. Window name == agent id == worktree leaf.
- **OQ4 — Registry surface: human CLI + docs for v1.4.0; `session --json` deferred to v1.4.1.** Keep the first release lean; a machine-readable JSON registry earns its place only after the CLI shape is proven in real use.

## Release path (governed, unchanged)
Branch off `main`; TDD per task; freeze immutable candidate (disposable-index diff + tree + SHA-256); independent review (security / functional-mutation / docs) all-PASS on identical bytes; real devbox smoke; on explicit "go": push, tag `v1.4.0`, publish, byte-verify public files. No push/tag/release/deploy without explicit authorization.

## Risks & tradeoffs
- **Shared-worktree collisions** — mitigated by the per-worktree turn-lock (advisory; document the failure mode).
- **Worktree sprawl** — `remove` must clean tmux window + git worktree + branch together; `list` keeps it visible.
- **Chat can't mirror a live TUI** — scoped out (D5).
- **Each channel widens terminal authority** — but channel auth is Hermes config, not ours; we document the boundary and defer enforcement to Hermes.
- **Telegram UX change** (D6) — real shift for existing users; release-notes callout.
- **No live tmux/daemon in the build/review container** — static + mutation here; real multi-channel/multi-agent smoke on a devbox before release.
